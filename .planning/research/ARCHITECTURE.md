# Architecture Research

**Domain:** учебный снимок инициализации GSD поверх готового канбана
**Researched:** 2026-10-05
**Confidence:** HIGH

## Standard Architecture

Рантайм канбана уже описан в `.planning/codebase/ARCHITECTURE.md` и в этом снимке не меняется. Ниже — как документы планирования садятся рядом с этим рантаймом, чтобы слушатель видел границу.

### Structure Rationale

- **`apps/` и `packages/`:** единственный рантайм. Два процесса и `@repo/shared`. Новые пакеты и каталог `src/` под планирование здесь не появляются.
- **`docs/`:** человеческая документация доски. Нумерация `00–04` и `adr/` уже задаёт, куда класть гайд продукта. Документы GSD сюда не переносятся.
- **`docs/_ai/`:** тот же продукт короче, с фиксированным порядком чтения для агента. Это источник фактов о доске, а не вторая копия `.planning/`.
- **`.planning/codebase/`:** карта для brownfield-команд GSD. Она пересказывает рантайм и раскладку файлов. Она не заменяет `docs/01-architecture/` и не задаёт целевую архитектуру.
- **`.planning/research/`:** четыре параллельных входа и одна сводка. Сводка — единственный файл исследования, который роадмап обязан прочитать целиком.
- **Корень `.planning/`:** `PROJECT.md`, `config.json`, затем `REQUIREMENTS.md`, `ROADMAP.md`, `STATE.md`. Так устроен канонический набор `/gsd-new-project`.
- **`.cursor/rules/`:** остаётся правилами агента (Memory Bank, коммиты, graphify). Генерация instruction-файла из шага roadmap в этот снимок не входит: она смешала бы правила агента со слоем урока.

## Architectural Patterns

### Pattern 1: Три двери, один рантайм

**What:** У репозитория три входа, и каждый ведёт в свой слой. Слушатель снимка начинает с `.planning/PROJECT.md`. Человек, который запускает доску, начинает с `docs/00-start/`. Агент, который правит код доски, начинает с `docs/_ai/README.md` (так задано в `.cursor/rules/memory-bank.mdc`). Все три входа описывают или ограничивают один и тот же рантайм.

**When to use:** Всегда в этом снимке. Смешивать двери — значит спрятать границу, ради которой снимок собран.

**Trade-offs:** Слушатель видит три файла со словом «архитектура». Это цена явной границы. Выигрыш: по пути файла понятно, чей это документ. `docs/_ai/architecture.md` — короткий снимок продукта. `docs/01-architecture/` — длинные гайды продукта. `.planning/codebase/ARCHITECTURE.md` — as-is карта для GSD. Этот файл — как документы урока лежат рядом с доской.

**Example:**

```text
Слушатель снимка     →  .planning/PROJECT.md
Запуск доски         →  docs/00-start/local-setup.md
Агент в коде доски   →  docs/_ai/README.md
Карта для GSD        →  .planning/codebase/ARCHITECTURE.md
```

### Pattern 2: Карта brownfield до исследования

**What:** Сначала фиксируется то, что уже работает (`.planning/codebase/`), затем `PROJECT.md` отделяет проверенные способности доски от активной цели снимка. Исследование читает эту карту и не предлагает новый процесс, слой сервисов или второй контракт задачи.

**When to use:** Репозиторий уже содержит канбан. В `PROJECT.md` это решение записано: карта кодовой базы предшествует проектному документу.

**Trade-offs:** Исследование получается короче и жёстче, чем обзор «как вообще строят канбан». Для воркшопа это нужная жёсткость. Обзор экосистемы канбана в этот снимок не добавляет компонентов.

**Example:**

```text
.planning/codebase/ARCHITECTURE.md   # as-is, уже записан
        ↓ читают все четыре исследования
.planning/research/*.md
        ↓ только сводка
.planning/research/SUMMARY.md
        ↓
REQUIREMENTS.md → ROADMAP.md + STATE.md
```

### Pattern 3: Роадмап как документ, каталог фаз — в следующем снимке

**What:** `ROADMAP.md` в этом снимке описывает фазы. Каталога `.planning/phases/` ещё нет. Исполнение фазы — следующий снимок воркшопа, не эта инициализация.

**When to use:** Активная цель `PROJECT.md`: в `.planning/` лежат конфиг, исследование, требования v1, роадмап и состояние. Вне объёма: исполнение фаз, новые возможности доски, пары веток as-is/to-be.

**Trade-offs:** Слушатель видит план и одновременно видит, что плана в `phases/` нет. Это и есть завершённая инициализация. Пустой каталог `phases/` создавать не нужно: пустая папка выглядит как начатое исполнение.

**Example:**

```text
Есть в снимке:     .planning/ROADMAP.md
                     .planning/STATE.md со статусом «фаза не начата»
Нет в снимке:      .planning/phases/**
                     правки apps/** и packages/**
```

## Data Flow

Два потока. Их нельзя рисовать одной стрелкой.

Поток доски (заморожен, направление одно):

```
Браузер
    ↓
Vite :5173  →  proxy /api (префикс срезается)
    ↓
Fastify :3001  →  функции в db.ts  →  apps/backend/data/tasks.db
    ↑
@repo/shared — типы на этапе компиляции, не рантайм-шина
```

Сервер остаётся источником правды после каждой мутации. Клиент держит доску в `useState` внутри одного компонента. `PATCH /tasks/:id` и клиентский `updateTask` есть; доска их не вызывает. Исследование это не «доделывает».

Поток урока (что открывает слушатель):

```
.planning/PROJECT.md
    ↓ зачем снимок и что код доски не меняется
docs/_ai/architecture.md + docs/_ai/data-flow.md
    ↓ тот же канбан, коротко
.planning/codebase/STRUCTURE.md
    ↓ где лежат слои
.planning/codebase/ARCHITECTURE.md
    ↓ as-is рантайм для GSD
.planning/research/SUMMARY.md
    ↓ после того как сводка собрана из четырёх файлов
.planning/REQUIREMENTS.md
    ↓
.planning/ROADMAP.md
    ↓
.planning/STATE.md
```

`docs/README.md` и `docs/00-start/` слушатель открывает, когда хочет запустить доску. Это четвёртая остановка по желанию, не шаг сюжета инициализации. `docs/01-architecture/` — справочник за Memory Bank, не обход карты `.planning/codebase/`.

### Request Flow

Запрос урока идёт сверху вниз по документам. Обратной записи нет.

```
Слушатель
    ↓
PROJECT.md
    ↓
docs/_ai (продукт)  →  codebase/ (карта того же продукта)
    ↓
research/STACK + FEATURES + ARCHITECTURE + PITFALLS
    ↓
research/SUMMARY.md
    ↓
REQUIREMENTS.md  →  ROADMAP.md  →  STATE.md
```

Направление записи при сборке снимка совпадает с этим порядком. `research/` не правит `docs/_ai` и не правит `apps/`. `REQUIREMENTS.md` не создаёт маршруты. `ROADMAP.md` не создаёт каталог `phases/`.

### State Management

Состояние снимка — файлы, не процесс.

```
PROJECT.md          что уже правда о доске и что снимок ещё должен показать
    ↓
research/SUMMARY.md выводы для фаз (документ)
    ↓
REQUIREMENTS.md     v1 урока и трассировка на фазы
    ↓
ROADMAP.md          фазы и критерии
    ↓
STATE.md            текущая позиция: инициализация собрана, исполнение не начато
```

Состояние доски живёт отдельно: один sqlite-файл и `useState` в `App`. `STATE.md` его не отражает и не заменяет. `config.json` хранит режим GSD (`interactive`, `granularity: standard`, `commit_docs: true`) и не хранит задачи канбана.

`docs/_ai/README.md` сейчас содержит фразу, что каталогов `graphify-out/` и `.planning/` в репозитории нет. Это след Memory Bank, снятого с продукта до появления планирования. В этом снимке фразу не исправляют: правка превратила бы продуктовый снимок в оглавление GSD. Расхождение само показывает границу слоёв.

### Key Data Flows

1. **Узнать, что доска уже умеет.** `PROJECT.md` (раздел Validated) и `.planning/codebase/ARCHITECTURE.md`. Источник фактов о запросе — `docs/_ai/data-flow.md`. Новый поток данных для задач не проектируется.
2. **Увидеть границу слоёв.** Слушатель сравнивает путь файла. Код — `apps/` и `packages/`. Продукт словами — `docs/` и `docs/_ai/`. Урок — `.planning/`. Одинаковое имя `ARCHITECTURE.md` в трёх местах — три роли, см. Pattern 1.
3. **Собрать оставшиеся документы инициализации.** Порядок в подразделе Build Order. Параллельны только четыре файла `research/`. `SUMMARY.md` ждёт все четыре. `ROADMAP.md` и `STATE.md` пишутся одним шагом после требований.

### Build Order

Уже записано и в этом снимке повторно не производится:

1. `.planning/codebase/` — семь карт as-is.
2. `.planning/config.json`.
3. `.planning/PROJECT.md`.

Остаток инициализации, только документы:

4. Параллельно: `research/STACK.md`, `research/FEATURES.md`, `research/ARCHITECTURE.md`, `research/PITFALLS.md`. Каждый читает `PROJECT.md` и карту кодовой базы. Ни один не пишет в `apps/`, `packages/`, `docs/`.
5. `research/SUMMARY.md` — после четырёх. Это единственный синтез, который читает роадмап. Писать сводку параллельно с четырьмя файлами нельзя.
6. `REQUIREMENTS.md` — после сводки и `FEATURES.md`. Требования v1 описывают, что слушатель видит в снимке инициализации. Способности доски, уже помеченные в `PROJECT.md` как Validated, в v1 как новая работа не ставятся. Категории требований берутся из исследования фич, ограниченного «код доски не меняется».
7. Одним шагом: `ROADMAP.md`, `STATE.md`, таблица трассировки в `REQUIREMENTS.md`. Роадмап читает `PROJECT.md`, `REQUIREMENTS.md`, `research/SUMMARY.md`, `config.json`. Каждая v1-требование попадает ровно в одну фазу. `STATE.md` фиксирует: документы инициализации на месте, каталога фаз нет, исполнение не начато.
8. Коммит документов планирования — дело оркестратора после всех исследований. Этот файл не коммитится отдельно.

В снимок не входят, даже если общий воркфлоу GSD это умеет:

- каталог `.planning/phases/` и любые `PLAN.md`;
- `MILESTONES.md`, `RETROSPECTIVE.md`, архив `milestones/`;
- перегенерация `.cursor/rules/` или `AGENTS.md`;
- правка `docs/` и `docs/_ai/`;
- вертикальная нарезка «БД → API → UI»: доска уже собрана сквозным срезом, горизонтальные слои выглядели бы как переписывание;
- граф `graphify-out/graph.json` — он на ветке `01-graphify`, не на этом снимке `main`.

Режим фаз в `ROADMAP.md`: ближе к вертикальному срезу урока (слушатель за один заход видит весь контур инициализации), а не к сборке технических слоёв канбана. Успех фазы в этом снимке — наблюдаемое состояние репозитория (файл лежит, код доски тот же), а не новая кнопка на доске.

## Scaling Considerations

Масштаб здесь — число документов воркшопа, а не число пользователей доски. Монолит из двух процессов для демо остаётся достаточным на всех ступенях ниже.

| Scale | Architecture Adjustments |
|-------|--------------------------|
| Этот снимок (инициализация) | Корень `.planning/`, `codebase/`, `research/`. Рантайм и `docs/` не трогать. `phases/` не создавать |
| Следующий снимок (план фазы) | Появляется `.planning/phases/NN-*/` с планом. Код доски по-прежнему можно не менять, если урок — про план |
| Снимок исполнения | Рядом с планом появляется summary исполнения. Вот тогда меняется `apps/` или `packages/`, и следом имеет смысл обновить `docs/_ai/` |
| Несколько вех | Архив в `.planning/milestones/`. Рантайм по-прежнему два процесса и один sqlite-файл |

### Scaling Priorities

1. **Первая поломка — три «архитектуры» без подписи роли.** Слушатель открывает `docs/_ai/architecture.md`, `docs/01-architecture/` или `.planning/codebase/ARCHITECTURE.md` и решает, что это три проекта. Лечится порядком чтения из Pattern 1 и тем, что этот файл не дублирует карту рантайма.
2. **Вторая поломка — синхронизация Memory Bank с `.planning/`.** Желание поправить фразу «каталога `.planning/` нет» в `docs/_ai/README.md` понятно и в этом снимке вредно. Memory Bank обновляется, когда меняется поведение доски, а не когда рядом появляется план.

## Anti-Patterns

### Anti-Pattern 1: Вторая архитектура доски внутри research

**What people do:** По шаблону исследования рисуют controller → service → repository и предлагают вынести SQL из `db.ts`.

**Why it's wrong:** Карта кодовой базы уже фиксирует отсутствие слоя сервисов. Новый слой в снимке инициализации неотличим от фичи. Слушатель перестаёт видеть границу «канбан был / GSD добавился».

**Do this instead:** В исследовании архитектуры описывать документы и порядок чтения. Рантайм цитировать из `.planning/codebase/ARCHITECTURE.md` одной схемой: браузер → Vite → Fastify → sqlite.

### Anti-Pattern 2: Перенос GSD в `docs/`

**What people do:** Кладут роадмап в `docs/01-architecture/` или дописывают фазы в `docs/_ai/architecture.md`, потому что «документация должна быть в одном месте».

**Why it's wrong:** `docs/` — гайды продукта с собственной картой (`docs/README.md`). `.planning/` — канонические артефакты команд GSD (`PROJECT.md`, `REQUIREMENTS.md`, `ROADMAP.md`, `STATE.md`, `research/`, `codebase/`). Смешение ломает и онбординг человека, и команды, которые ищут файлы по фиксированным путям.

**Do this instead:** Продукт остаётся в `docs/` и `docs/_ai/`. Урок остаётся в `.planning/`. Связь между ними — ссылка и порядок чтения, а не копирование текста.

### Anti-Pattern 3: Исполнение внутри снимка инициализации

**What people do:** Вместе с `ROADMAP.md` создают `.planning/phases/01-*/PLAN.md` или сразу меняют доску «чтобы фаза 1 была зелёной».

**Why it's wrong:** Активное требование снимка — увидеть завершённую инициализацию. Исполнение фаз отнесено к следующим снимкам. Ранний план или правка `App.tsx` склеивает два урока в один коммит.

**Do this instead:** Остановиться на `STATE.md`. В состоянии явно записать, что фаза не начата и каталога `phases/` нет.

### Anti-Pattern 4: Обновить правила агента «заодно»

**What people do:** На шаге роадмапа перегенерировать instruction-файл в `.cursor/rules/` или дописать в `AGENTS.md` оглавление `.planning/`.

**Why it's wrong:** `AGENTS.md` в этом репозитории — служебное уведомление Turborepo, без проектных правил приложения. Правила агента уже задают чтение `docs/_ai/` перед задачей в коде. Новый сгенерированный блок делает вид, что вход агента и вход слушателя — один файл.

**Do this instead:** Оставить `.cursor/rules/` и `AGENTS.md` как есть. Вход слушателя — `PROJECT.md`. Вход агента в код доски — `docs/_ai/README.md`.

## Integration Points

### External Services

| Service | Integration Pattern | Notes |
|---------|---------------------|-------|
| Команды GSD на машине слушателя | Читают и пишут только `.planning/` | Инициализация: questioning → research → requirements → roadmap. Brownfield начинается с карты `codebase/`. Сети для этой границы нет |
| Доска в браузере | Уже встроена: Vite proxy `/api` → Fastify | Этот снимок proxy, порты 5173/3001 и файл `tasks.db` не меняет |
| graphify | Отдельная ветка `01-graphify` | На `main` в этот снимок граф не входит. `graphify-out/graph.json` для урока инициализации не нужен |
| Git | `commit_docs: true` в `.planning/config.json` | Документы `.planning/` коммитятся в репозиторий, чтобы слушатель увидел их в снимке. Пуш и ветка-снимок — после того как набор инициализации собран, не из этого файла |

Внешних API у урока нет. Аутентификация, OpenAPI, очереди и CI в приложение инициализацией не добавляются.

### Internal Boundaries

| Boundary | Communication | Notes |
|----------|---------------|-------|
| `apps/frontend` ↔ `apps/backend` | HTTP `/api` через proxy Vite | Приложения не импортируют друг друга. Граница уже есть, в снимке не обсуждается заново |
| Оба приложения ↔ `@repo/shared` | Компиляция, одно направление | Контракт задачи один. Дублировать `Task` в приложение или в `.planning/` нельзя |
| `apps/backend/src/index.ts` ↔ `db.ts` | Прямой вызов функций | Слоя сервисов нет. Новые операции доски, когда они появятся в другом снимке, остаются функцией в `db.ts` и маршрутом в `index.ts` |
| `.planning/codebase/` → рантайм | Только описание | Карта читает код. Код карту не читает |
| `.planning/research/` → `codebase/` и `PROJECT.md` | Чтение | Исследование не перезаписывает карту и не правит продукт |
| `SUMMARY.md` → роадмап | Единственный синтез | `ROADMAP.md` опирается на сводку, а не на четыре сырых файла по отдельности |
| `docs/_ai/` → `docs/00–04` | Ссылки, без копирования гайдов | Memory Bank остаётся сжатым. Длинный рассказ — в нумерованных разделах |
| `docs/` ↔ `.planning/` | Рядом в одном репозитории, без генерации | Ни один слой не собирается из другого скриптом |
| Слушатель ↔ агент кода | Разные первые файлы | Слушатель: `PROJECT.md`. Агент в коде: `docs/_ai/README.md` |
